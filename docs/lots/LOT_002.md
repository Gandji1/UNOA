# Lot 002 — Base de données et droits par portée

Relu le 19 novembre 2026. TdR sections 1 à 4, 16 à 24, et modules CORE, TEN, IAM, SEC et OPS. Références complémentaires dans les contrats de données, le paramétrage régional, la matrice d’accès et le prototype validé. L’écran « Paramètres et versions » du prototype guide les futures interfaces de configuration par portée et par date.

| Exigence | Périmètre de ce lot | Vérification |
|---|---|---|
| REQ-CORE-002, 003, 007, 009 | PostgreSQL local, migrations SQL atomiques, contrôle d’intégrité et séparation des accès | Base vierge, reprise, concurrence, dérive et échec |
| REQ-TEN-001, 007 | Types administrables et hiérarchie des portées | Création de deux territoires fictifs et rejet d’un lien incohérent |
| REQ-IAM-001, 006, 007, 010 | Identités externes, rôles composables et autorisations datées par portée | Accès direct, délégation descendante explicite, expiration, révocation et refus transversal |
| REQ-SEC-008 | Journal d’audit en ajout seul | Rejet des modifications, suppressions et vidages |
| REQ-OPS-001, 005 | Contrôles automatisés du socle et vérifications web | Tests PostgreSQL et sondes HTTP |

Les migrations sont exécutées avec un compte propriétaire distinct des accès applicatifs. Elles créent les schémas sans programmes, utilisateurs ou territoires préremplis. Les valeurs fictives entrent uniquement dans une base éphémère créée par les tests. Le contrôle de permission s’exécute pour un identifiant acteur déjà authentifié côté serveur. Le raccordement OIDC, les politiques RLS sur les futures tables métier et l’écran d’administration font l’objet des lots suivants. Aucune route d’administration n’est ouverte.

En cas d’échec, la transaction de migration est annulée. Après application, corriger par une migration suivante et tester la restauration avant toute opération sur une base institutionnelle.
